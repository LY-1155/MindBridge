# 知识路由内嵌对话式量表筛查

知识路由（knowledge）下引入标准化心理筛查量表（PHQ-9、GAD-7 等），由 LLM 以自然对话方式引导用户自评，得分达到阈值后作为知识库检索的强化上下文。

## 为什么

- **量表结果为知识检索提供精确上下文**。PHQ-9 测出中重度抑郁后，检索词"抑郁情绪管理 + 中重度"比泛泛搜索"抑郁"更精准。
- **对话式施测而非逐字念题**。直接念量表原文（"在过去两周内，你有多少时候..."）是机器人的做法，用户反感。由 LLM 根据对话上下文自然地引出症状询问，用户体验好，信息价值等价。
- **筛查结果标注为"自评参考"而非诊断**。LLM 对话中的量表施测未经临床验证，不能等同于医生面诊中使用的标准化工具。自评结果仅供参考，不可替代专业诊断。
- **选 11 个而非全部 20 个候选量表**。排除了：临床评定量表（MADRS、HAM-D，需医生观察）、版权收费量表（BDI）、冗余量表（HCL-32 被 MDQ 覆盖）、50 题以上体验稀烂的量表（AQ-50）、以及安全上不可接受的自杀风险筛查量表（C-SSRS、ASQ，让 LLM 施测自杀量表是责任事故）。

## 考虑过的方案

- **不引入量表**：知识路由只做知识库检索 + LLM 科普，缺少对用户具体情况的评估锚点。知识检索的查询词缺乏定向，容易输出泛化内容。不选。
- **量表作为独立管线阶段**：在 router 和 intervention 之间插入一个新的"Screening Stage"。优点是模块边界清晰，缺点是把一个干预子功能提升为管线必选阶段，对于不适用量表的请求（如直接知识问题）是浪费。不选。
- **逐字念量表原文**：保证量表标准化，但用户体验差。且标准化是假象——LLM 聊天环境本身已破坏了量表施测的标准化条件。不选。

## 决策

以下 11 个决策点确定了量表筛查的全部行为边界。决策编号对应 grilling session 中的问题顺序。

### D1 — 触发条件：LLM 分类 + 情绪阈值双重判定

路由必须是 `knowledge`。在 knowledge 分支内，使用 LLM 做症状叙述 vs 知识提问的二分类，配合 `primary_emotion` 的 intensity 阈值做安全门槛（过低不触发）。两个条件同时满足才启动量表。

- 拒绝：纯阈值判定（丢失语义，用户说"什么是抑郁症"情绪也可能低但不应触发量表）
- 拒绝：纯 LLM 判定（缺少保底门槛，低 intensity 不值得用量表评估）

### D2 — 多轮对话式施测

量表采用多轮交互，每轮嵌入 1-2 道量表题目，穿插在正常对话中。需要会话状态追踪（当前量表、第几题、累计得分），但管线整体保持无状态——量表状态存于 `TherapySessionMemory`。

- 拒绝：单轮推断（用户信息不完整，评估不准确）

### D3 — 自然引入，不告知

量表启动时不告知用户"正在做问卷"。由 LLM 根据对话上下文自然过渡，以共情询问的语气引出第一道维度。用户拒绝/表现出排斥时不宜进一步说明——静默放弃该轮量表触发。

- 拒绝：透明告知（"现在我给你做一个 PHQ-9 量表"——引发防御和抗拒）
- 拒绝：告知后征得同意（同上，且增加摩擦）

### D4 — 结果同时反馈给用户和注入检索

量表完成后：以自然语言包装将结果融入当轮回复（不报原始分数，不说"PHQ-9 得分 15"），同时将分级关键词（如"中重度抑郁"）注入后续 RAG 检索查询。

- 拒绝：静默检索不反馈（用户有权知道自己被评估了什么）
- 拒绝：只反馈不注入检索（浪费了量表提供的精准查询信号）

### D5 — 量表选择：LLM 语义匹配替代 emotion 硬映射

**旧方案**：按 `primary_emotion` 硬映射到单一量表（sadness → PHQ-9，anxiety → GAD-7），其余情绪不触发。问题：(1) 11 个量表中仅 2 个可用，其余 9 个永不触发；(2) 抑郁和焦虑共病率 60-70%，sadness 用户可能同时有焦虑症状却只做 PHQ-9；(3) 扁平 emotion 标签无法表达症状的丰富性。

**新方案**：LLM 阅读用户发言，与 11 个量表的 name + description 进行语义匹配，输出匹配度最高且存在实质关联的量表名列表（按 relevance 排序）。prompt 中列出所有可用量表及其描述，LLM 仅做匹配，不虚构。

输入：user_text + 量表目录（name, display_name, description）
输出：`{"trigger": true/false, "scales": ["PHQ-9", "GAD-7"], "reason": "..."}`

匹配规则：
- 用户发言中的症状线索 vs 量表 description 语义相近 → 匹配
- 找不到任何匹配 → trigger: false，不凭空推荐
- 多量表匹配时按 relevance 排序

- 拒绝：emotion 硬映射（锁死 2/11 个量表，无视共病，不应继续用）
- 拒绝：固定组合（不根据用户实际症状，盲目串行多个量表）
- 保留：intensity >= 0.4 阈值作为安全门槛（避免低强度下过度筛查）

### D6 — 分数可作为安全升段信号

量表总分达到重度阈值（PHQ-9 ≥ 20）或第 9 题（自伤念头）≥ 1 分时，触发路由重评估，可能上升到 `crisis`。中重度以下保持 `knowledge`，仅增强检索信号。

- 拒绝：不改路由只改检索（丢失量表提供的安全信号——这是情绪分析做不到的）
- 拒绝：任何分数都升段（过度触发危机，稀释危机通道的严肃性）

### D7 — 偏离话题处理：灵活衔接，连续偏离则静默放弃

用户偏离量表话题时：LLM 先自然回应偏离内容，同时在回复末尾轻柔嵌入下一题。连续 2 轮以上偏离则静默放弃当前施测，量表状态标记为"未完成"，转入正常 knowledge 干预。

- 拒绝：强制拉回量表（侵犯用户对话主导权）
- 拒绝：一偏离就中断（过于敏感，一次离题可能只是自然的对话过渡）

### D8 — 计分与生成分离：独立 LLM 调用做计分

每轮量表题目的用户回复由独立的轻量 LLM 调用进行计分（根据锚点判定 0-3 分），与主对话 LLM 调用分离。如果用户回复明显不匹配当前题目的维度，计分 LLM 可返回 -1 表示无效。

- 拒绝：主 LLM 同时计分（对话风格和责任冲突，prompt 容易被对话策略污染）
- 拒绝：全部题目做完后统分（丢失逐题计分的中间验证机会，且末尾汇总压力大）

### D9 — 量表结果持久化到会话

量表结果写入 `TherapySessionMemory.SessionMetadata`，跟着现有会话持久化通路（内存/Redis/MySQL）走，不需要新增存储层。会话结束后量表数据跟随会话生命周期。

- 拒绝：独立量表记录表（需要用户体系和跨会话关联，当前项目架构不支持，提前做是过度设计）
- 拒绝：仅内存存活（会话重启丢失，不可追溯）

### D10 — 共病场景允许串行，自动接续但带放弃保护

LLM 返回多量表列表时（如 `["PHQ-9", "GAD-7"]`），按列表顺序串行执行：

1. 启动第一个量表，正常多轮施测
2. 完成后自动过渡到下一个量表："你刚才也提到了担心方面的情况，我们再了解几个方面..."
3. 用户说"不要"、"先不谈"、"太多了" → 立即放弃后续量表，scale_state 标 abandoned
4. 现有 wander_count 连续 2 次偏离退出机制照常生效

这样既覆盖共病场景，也不绑架用户。

- 拒绝：同时交错出题（两个量表第 1 题轮流问，用户感知混乱，状态管理极复杂）
- 拒绝：不做任何串行，共病场景只测一个量表（漏掉重要症状维度）
- 接受：会话内重新触发（如果用户后续暴露新症状，可再次经过 D1 判定触发新量表）

### D11 — 量表题本存储为 JSON 配置文件

量表题本（维度名、症状概念范围、0-3 计分锚点、分级阈值）以结构化 JSON 存放在 `data/knowledge/private/scales/` 目录下。不是提示词模板，是结构化判定依据，供主 LLM（理解维度边界生成自然询问）和计分 LLM（对照锚点打分）分别使用。

- 拒绝：存为 Python dataclass（量表数据应由心理专业人员审核维护，JSON 更友好）
- 拒绝：存入知识库作为自然语言条目（量表是工具配置，不是参考知识，语义类别不同）

## 架构位置

```
modules/intervention/
├── service.py              ← knowledge 分支插入量表 hook（判断触发 → ScaleOrchestrator）
├── generator.py            ← 不变，仍负责 comfort/knowledge 的 LLM 生成
├── crisis_handler.py       ← 不变
├── rag/retriever.py        ← 不变，检索词可被量表结果增强
└── scale/
    ├── __init__.py
    ├── orchestrator.py     ← 量表生命周期：启动/选题/计分/判定完成/放弃
    ├── scorer.py           ← 独立计分 LLM 调用（对照锚点 0-3 或 -1 无效）
    └── models.py           ← ScaleState, ScaleItem, ScaleResult 数据类

data/knowledge/private/scales/
├── phq9.json               ← 9 道题的 dimension/concept/anchors/thresholds
├── gad7.json               ← 7 道题
└── ...                     ← 其余 9 个量表

core/memory/session_memory.py
└── SessionMetadata.scale_state: Optional[Dict]  ← 新增字段

schemas/contracts/v1.py
└── InterventionResult.meta  ← 复用现有字段，量表事件通过 meta 传递
```

## 可观测性

- **结构化日志**：量表关键事件（START / Q_N / DONE / ABANDON）以 `[SCALE:EVENT]` 前缀输出结构化日志，开发者终端可 `tail -f` 实时观察
- **会话状态查询**：量表状态（进行中/已完成/得分/题号）通过 `SessionMetadata.scale_state` 暴露，可通过现有 `GET /api/v1/session/{id}` 查询
- **流式推送**：如果前端需要实时监听，在 SSE stream 中嵌入 `scale_event` 类型事件
