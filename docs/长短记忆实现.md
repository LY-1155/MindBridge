## 0. 一句话讲清架构

> 这个 Agent 把记忆分成五层：**上下文窗口**（短期/工作记忆）、**原始消息日志**（情景记忆）、**蒸馏的临床状态**（语义记忆）、**确定性状态机**（程序性记忆）、**RAG 知识库**（外部记忆）。前两层负责"记住发生过什么"，第三层负责"从对话里提炼出结构化结论"，第四层保证高风险行为不靠模型记忆，第五层补足训练集外的知识。存储上采用 **Redis 热缓存 + MySQL 冷持久化**的双层结构。上下文窗口内部再分两级：**LLM 滚动摘要**（早期对话压缩，对标 MemGPT working/summary）+ **最近 N 轮原文**（按 token 预算自适应截取）。

## 2. 短期 / 工作记忆（Working / Scratchpad Memory）＝ 上下文窗口

**本质**：不是模型"记得"，而是每轮请求把压缩后的上下文**显式写进 prompt**。相当于医生每次进诊室前，把病历和上次记录摊在桌上。

### 拼装点（[generator.py:389](modules/intervention/generator.py#L389) `_get_format_kwargs`）

每轮生成回复时，把以下内容拼成 system prompt：

| 注入段 | 来源 | 作用 |
|---|---|---|
| `conversation_history` | [generator.py:275](modules/intervention/generator.py#L275) `_format_history` | 摘要前缀（`get_context_summary()` 事实摘要 + LLM 滚动摘要）+ 最近 N 轮原文（按 `HISTORY_TOKEN_BUDGET` token 预算自适应选轮） |
| `probed_dimensions_note` | `_get_probed_dimensions_text` | 已探测/未探测的 6 个临床维度，告诉 LLM"问过的别重复" |
| `assessor_context` | [session_memory.py:527](core/memory/session_memory.py#L527) `get_assessor_context` | 语义记忆转文本：当前阶段/工作假设/家庭成员 |
| `phase` | `_get_session_phase` | 会话阶段（check_in / explore / interpret / intervene） |
| `retrieved_knowledge` | RAG | 检索到的知识库内容 |
| `zhou_style_refs` | 周医生风格 RAG | DOCTOR_MODE 下注入风格参考 |
| `scid_directive` | `_format_scid_directive` | SCID 访谈状态机产出的"本轮访谈指令" |
| `safety_probe` | `_get_safety_probe` | 危机评估器产出 probe 时的安全探针指令段 |

### 为什么是"窗口"而不是"模型记忆"

- **显式、可控**：每轮重新拼装，不依赖 LLM 在长上下文里自行记住。
- **有界（token 预算自适应）**：历史按 `HISTORY_TOKEN_BUDGET`（默认 2000 token）动态选「摘要 + 最近 N 轮原文」，上下文不随对话无限增长。选轮用 tiktoken cl100k_base 近似计数（Qwen BPE 的近似，预算留安全余量；tiktoken 不可用回退字符启发式），自最近往早选完整轮次，至少保留最近一轮。
- **滚动摘要分层（对标 MemGPT working/summary）**：每 `SUMMARY_EVERY_N_TURNS`（默认 8）轮，用轻量模型（`SUMMARY_MODEL_NAME`，enable_thinking=false）把「旧摘要 + 最近几轮」合并成新摘要，存进 `metadata.rolling_summary`。prompt 里摘要放最前面，最近原文放后面——早期对话不丢、上下文又不膨胀。危机路径绝不触发摘要（零延迟铁律）。
- **语义记忆进窗口，流水账不进**：prompt 只吃"蒸馏出的结论 + 最近几轮"，不吃全部原始日志（见第 4 节）。

## 3. 情景记忆（Episodic Memory）＝ 原始消息日志

记录"实际发生了什么"的原始流水账，**不直接全部塞进 prompt**。

### 存储

- **MySQL `messages` 表**（[database_v2.py](schemas/database_v2.py) `MessageV2`）：每条消息 `content` **AES 加密**后存（[db_storage.py:205](core/memory/db_storage.py#L205)）。
- **Redis `psy:session:{id}:msgs` LIST**（[redis_storage.py:112](core/memory/redis_storage.py#L112) `cache_message`）：LPUSH 写入、LRANGE 读回，cap 40 条，TTL 1h。

### 读写路径

```
写：add_message() → use_database=true：MySQL add_message + Redis cache_message
                     use_database=false：仅进程内存（纯内存模式）
读：get_messages() → use_database=true：Redis 优先 → MySQL 回退
                     use_database=false：仅进程内存
```

### 关键设计

- **Redis 是热缓存，MySQL 是真相源**：Redis 快，扛高频读；MySQL 耐久，Redis 挂掉/TTL 过期可从库还原。
- **消息与蒸馏状态分离**：`messages` 表只存原文；跨轮的结构化结论存在 `SessionMetadata`（下一节）。这就是"情景记忆"与"语义记忆"的分工。

---

## 4. 语义记忆（Semantic Memory）＝ 蒸馏的临床状态

**这是最核心、也最适合当面试亮点的一层。**

### 数据模型（[session_memory.py:34](core/memory/session_memory.py#L34) `SessionMetadata`）

Pydantic v2 模型，字段都是"从对话里提炼出的结构化事实"：

```python
class SessionMetadata(BaseModel):
    model_config = ConfigDict(extra="ignore")

    session_id: str
    user_id: Optional[str] = None
    created_at: datetime
    last_active: datetime
    message_count: int = 0
    emotion_history: List[Dict] = []
    key_topics: List[str] = []
    probed_dimensions: List[str] = []          # 已探测的临床维度
    scale_state: Optional[Dict] = None         # 量表单测进度
    scale_history: List[Dict] = []

    # ── 医生模式字段（DOCTOR_MODE=true）──
    phase: str = "check_in"                    # check_in/explore/interpret/intervene
    family_members: List[Dict] = []            # [{"role":"妈妈","label":"焦虑型",...}]
    working_hypothesis: Optional[str] = None   # "孩子不上学承担了转移父母冲突的功能"
    scid_flags: Dict = {}                      # {"MDD":{"criteria_met":[...],"count":2}}
    scid_interview_state: Optional[Dict] = None # SCID 访谈状态机
    safety_state: Optional[Dict] = None        # 危机状态机 {"status":...}

    # ── 滚动摘要（包 B：上下文工程）──
    rolling_summary: Optional[str] = None      # LLM 自然语言摘要（早期对话压缩）
    rolling_summary_turn: int = 0              # 最近一次摘要覆盖到的对话轮数
```

### 跨轮累积（不是覆盖，是合并）

- **SCID 追踪**：[session_memory.py:490](core/memory/session_memory.py#L490) `update_scid_flags` 做**并集合并**——新命中的 criteria 追加到已有集合，`count` 重新计算。跨多轮累计证据。
- **家庭成员**：`add_family_member` 按 `role` 去重，重复出现只更新标签，不重复记录。
- **探测维度**：`probed_dimensions` 只增不减——医生问过的维度绝不再问。

### 统一序列化（单一权威来源）

```python
def to_state(self) -> Dict[str, Any]:
    """整份状态 → JSON 安全 dict（datetime 自动 isoformat）。"""
    return self.model_dump(mode="json")

@classmethod
def from_state(cls, data: Dict[str, Any]) -> "SessionMetadata":
    """dict → 模型；缺失 key 自动填默认值；extra='ignore' 向前兼容。"""
    return cls.model_validate(data)
```

**为什么重要**：所有读写路径（MySQL、Redis、create_session、save_scale_state）只认这一个序列化器。历史上曾有四份**手写字段清单**（写/读各两份），字段集合不一致，直接导致蒸馏状态**从不落库**——这就是我们修过的 P0（见第 9 节踩坑案例）。

### 持久化

- **MySQL `sessions.state_json`**：整份状态 JSON **AES 加密**存单列（[db_storage.py:79](core/memory/db_storage.py#L79)），是权威来源。
- **Redis `psy:session:{id}` HASH 的 `state` 字段**：整份 JSON 明文热缓存（TTL 1h，每次访问刷新），与 MySQL 共用同一序列化器。
- 旧行的兼容列（key_topics/scale_state/scale_history 等）**保留写入**，兼容老读者。

### 消费：转成自然语言注入 prompt

[session_memory.py:527](core/memory/session_memory.py#L527) `get_assessor_context()`：

```python
def get_assessor_context(self) -> str:
    parts = [f"**当前会话阶段**：{self.metadata.phase}"]
    if self.metadata.working_hypothesis:
        parts.append(f"**当前工作假设**：{self.metadata.working_hypothesis}")
    if self.metadata.family_members:
        members_text = "、".join(...)
        parts.append(f"**已识别家庭成员**：{members_text}")
    return "\n".join(parts)
```

LLM 每轮都带着这份"医生档案"，不用每次重新理解病人。

## 5. 程序性记忆（Procedural Memory）＝ 确定性状态机

**这一层是纯逻辑，不靠 LLM 记忆。** 高风险行为用确定性状态迁移保证"只要满足条件就一定触发"。

### 5.1 危机状态机（[risk_anchors.py:140](modules/assessment/risk_anchors.py#L140) `transition_safety_state`）

- **纯函数**（无副作用），每轮由评估器裁决（`crisis` / `probe` / `no_risk` / `None`）驱动迁移，结果写回 `metadata.safety_state`。
- 状态：`NONE → PROBING → CRISIS`，携带 `probe_count` 和 `denial_mark`。

```
NONE    ─(P0 风险 / crisis 裁决)──────────────→ CRISIS
NONE    ─(有锚点 probe 裁决)──────────────────→ PROBING
NONE    ─(无锚点 probe，纯情绪宣泄)────────────→ 保持 NONE（收窄原则）
PROBING ─(用户确认计划/手段)──────────────────→ CRISIS
PROBING ─(用户否认/仅念头)────────────────────→ NONE（denial_mark 保留）
PROBING ─(多次有锚点 probe 复现，≥max_probe_count)→ CRISIS（累积升级）
PROBING ─(无锚点 probe)──────────────────────→ 保持 PROBING（不累积）
```

- **锚点收窄原则（ADR-0013）**：只有由风险锚点词（自杀/自伤/暴力等 tier p0/p1/p2）驱动的 `probe` 才累积升级；纯情绪宣泄（"好痛苦"反复出现）**不升级**——避免过度判定危机。

### 5.2 SCID 访谈状态机（[scid_interview.py:290](modules/assessment/scid_interview.py#L290)）

结构化诊断访谈（SCID-5 抑郁模块）的推进器：

```python
def _new_state():
    return {
        "module": "MDD", "status": "active", "step": "gate",
        "waiting": True, "criteria_confirmed": [],
        "criteria_denied": [], "reask_count": 0,
        "bipolar_positive": False, "conclusion": None,
    }
```

每轮 `engine.step_turn(state, user_text, passive_mdd)` 返回 `(new_state, directive)`，`directive` 经 [generator.py:362](modules/intervention/generator.py#L362) `_format_scid_directive` 格式化为追加到 system prompt 的指令块（一次只问一个问题、不暴露"我在按手册访谈"）。

### 5.3 程序性记忆如何联动行为

- [safety_judge.py:185](modules/assessment/safety_judge.py#L185)：`safety_state.status in ("CRISIS","PROBING")` 时**强制触发评估**，不受省 token 的跳过逻辑影响。
- 这正是 `safety_state` 丢失是 **P0** 的原因：状态机回到 NONE = 把危机病人当普通病人。

**面试话术**：危机升级这类高风险行为不能靠 LLM"碰运气记得"，用确定性状态机保证——只要状态是 CRISIS，就必然走安全流程。这是"程序性记忆"区别于其它记忆的关键：存的不只是"状态"，还有"如何迁移"的规则。

## 7. 存储架构：Redis 热缓存 + MySQL 冷持久化 + 内存兜底

### 写路径（状态一变化即双写）

```
update_phase / update_hypothesis / update_scid_flags / update_safety_state / ...
        │  session_memory.py 的 _save_to_database()
        ▼
MySQL：DatabaseStorage.save_session(session_id, metadata.to_state())
        └─ state_json = AES(json.dumps(state))    ← 权威真相源
Redis：save_session_meta(session_id, metadata.to_state())
        └─ HASH["state"] = json.dumps(state)       ← 热缓存，TTL 1h
```

### 读路径（Redis 优先 → MySQL 回退 → 进程内存）

```
get_session(session_id)
  ├─ DB 模式下：Redis 命中 state → from_state 重建
  ├─ Redis 未命中 → MySQL load_session（state_json 解密）→ 回填 Redis
  └─ 都失败 → 进程内 _memory_sessions 兜底（仅开发/无持久化环境）
```

### 为什么分层

| 层 | 特点 | 职责 |
|---|---|---|
| Redis | 快（内存），TTL 1h 自动过期，每次访问刷新 | 扛高频读、多 worker 共享 |
| MySQL | 耐久、可查、AES 加密 | 权威真相源，崩溃/扩容可还原 |
| 进程内存 | 零依赖 | 兜底，保证没 Redis/MySQL 也能开发调试 |

### 消息与状态的关系

- 消息走独立的 `messages` 表 + `psy:session:msgs` LIST（情景记忆）。
- 蒸馏状态走 `sessions.state_json` + `psy:session:{id}` HASH（语义记忆）。
- 两者解耦：消息是"原始录像"，状态是"病历结论"。

## 8. 其它值得讲的设计点

### 8.1 会话归属校验（[session_memory.py:95](core/memory/session_memory.py#L95)）

`_verify_session_ownership`：`get_session` 时校验 `metadata.user_id` 是否匹配，防止越权访问他人会话（多用户安全）。

### 8.2 纯内存模式与持久化模式

- `use_database=false`（开发/单元测试）：消息与状态只进进程内存，**严格不写 Redis**——消息读写按 `use_database` 门控（[session_memory.py:296](core/memory/session_memory.py#L296) `add_message`、[session_memory.py:334](core/memory/session_memory.py#L334) `get_messages`），避免泄漏到 Redis 造成跨实例串数据。
- `use_database=true`（生产）：Redis + MySQL 双写。

### 8.3 敏感数据加密

- `messages.content`、`sessions.state_json`、`emotion_records.context` 均 **AES 加密**存储（`encrypt_field` / `safe_decrypt_field`）。
- 心理咨询是医疗级数据，这是合规硬要求，也是面试加分点。

## 9. 踩坑案例（P0：蒸馏状态从不落库）—— 最能体现深度的谈资

**现象**：`USE_DATABASE=true` + 多 worker 部署时，每次请求 `get_session` 新建实例重载，医生模式的 `phase`、SCID 累积、危机状态机全部回到默认值——危机状态从 CRISIS 变回 NONE。

**根因**（两层）：
1. `sessions` 表**没有对应列**存这些蒸馏字段；
2. 更本质的：四份**手写字段清单**（session_memory 写、db_storage 写/读、redis_storage 写/读）字段集合不一致——存储层只认识其中一部分字段。

**修复**：
- 单列 `state_json`（AES）承载整份 `SessionMetadata`，Redis 用单一 `state` 字段；
- 所有读写路径统一走 `to_state() / from_state()` 一个序列化器；
- 新增 DB 版跨实例回归测试（[tests/test_session_memory_persistence.py](tests/test_session_memory_persistence.py)），断言蒸馏状态能跨"新请求新实例"完整恢复。

**面试怎么讲**：把"多 worker 下状态丢失、危机状态机回 NONE 的安全风险"讲出来，再说"用单一序列化器消灭字段清单漂移这一类 bug"。这证明你不是背概念，是真在生产场景踩过坑、知道取舍。

## 10. 面试问答速查

### Q1：Agent 的短期记忆和长期记忆怎么实现？
> 短期记忆 = 每轮请求显式拼进上下文窗口的内容，内部再分两级：**LLM 滚动摘要**（早期对话压缩，存 `metadata.rolling_summary`）+ **最近 N 轮原文**（按 `HISTORY_TOKEN_BUDGET` token 预算自适应截取），再加上蒸馏出的临床状态、状态机结果、RAG 检索结果。长期记忆分三层：情景记忆（原始消息，MySQL+Redis）、语义记忆（蒸馏的结构化结论，SessionMetadata → state_json）、程序性记忆（危机/SCID 状态机）。存储是 Redis 热缓存 + MySQL 冷持久化。

### Q2：为什么不用"把全部历史塞进 prompt"？
> 上下文会无限膨胀，成本、延迟、LLM 的注意力窗口都吃不消。所以做分层：原始流水账只留情景层，prompt 只吃蒸馏结论 + 最近 N 轮原文。更早的对话由滚动摘要承载——每 N 轮用 LLM 把「旧摘要 + 最近几轮」合并成新摘要，早期信息不丢、上下文又不增长。相当于医生看的是病历摘要而不是全部诊疗录像，且病历摘要本身会随病程持续更新。

### Q3：语义记忆是怎么"蒸馏"的？
> 每轮对话后，各模块把结论写回 SessionMetadata：SCID 追踪做 criteria 并集合并、家庭成员按 role 去重、探测维度只增不减、危机状态由确定性状态机迁移。都是结构化字段，不是让 LLM 写一段摘要。

### Q4：怎么保证长期记忆持久化的一致性？
> 单一序列化器 to_state/from_state，MySQL 与 Redis 共用同一份序列化结果；写路径双写，读路径 Redis 优先、MySQL 兜底、失败再回填。曾经踩过四份手写字段清单不一致导致状态不落库的坑，所以现在只留一份序列化逻辑。

### Q5：多用户隔离怎么做？
> sessions.user_id 是 NOT NULL 外键 → users.user_id；get_session 时 _verify_session_ownership 校验归属，不匹配抛 SessionOwnershipError。会话数据归属到用户，Redis/MySQL 双层都带归属约束。

### Q6：如果 Redis 挂了会怎样？
> 读路径回退 MySQL（真相源），功能不中断，只是变慢。Redis 是热缓存，TTL 1h，重建成本可控。进程内存兜底保证极端情况不崩。

### Q7：危机状态机为什么不用 LLM 判断而用确定状态机？
> 安全关键路径不允许"概率性"。确定性状态迁移保证：状态是 CRISIS 就必然触发安全流程，可测试、可审计、可解释。LLM 只产出"裁决"（crisis/probe/no_risk），状态迁移是纯函数。

## 11. 如果面试官想往深挖

- **prompt 缓存 / 减少 token**：语义记忆进 prompt 是因为它小；如果要再省，可以做摘要缓存。
- **多 worker 扩展**：Redis 承担跨实例共享；当前进程内兜底只适合单机，规模化需去掉。
- **Redis 连接池**：`_get_redis()` 目前每次新建客户端，规模化可做模块级连接池。
- **消息双写开销**：每条消息写 MySQL + Redis，可考虑异步/批处理。
- **记忆的衰减/合并**：已实现滚动摘要（`metadata.rolling_summary`，每 `SUMMARY_EVERY_N_TURNS` 轮 LLM 合并），早期对话压缩进摘要、最近 N 轮原文保留，对标 MemGPT working/summary。危机路径不触发（零延迟铁律）。进一步可加"关键事实"抽取层（如结构化风险事实列表），摘要之上再叠一层可检索的长期记忆。
