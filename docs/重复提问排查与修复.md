# 重复提问问题排查与修复报告

> 日期：2026-07-23
> 涉及模块：Emotion、Intervention、Session Memory、Scale Orchestrator

---

## 问题 1：风险评分低估（Undersensitive Risk Scoring）

**现象：** 用户输入"什么都不想干，手机玩着也没意思"，情绪分析模块给出 `risk=0.07`，路由至 KNOWLEDGE（知识解答）而非 COMFORT（安抚干预）。用户处于慢性绝望状态却被推送到科普路线。

**根因：** `KeywordEmotionEngine` 基于关键词词典做情绪分类，但缺少对"慢性化信号"（chronicity markers）的感知。"好不了""一两年""越来越严重""什么都不想干"这类表达不匹配现有关键词组，导致 `primary_emotion` 回落为 `neutral`，risk 基线为 0。同时 `EmotionService._compute_risk` 公式仅考虑 `emotion_base + intensity_weight + safety_weight`，缺少独立的慢性化维度。

**修复：**

- 文件：`modules/emotion/stub.py`
- 新增 `_CHRONICITY_KEYWORDS`（28 个慢性/绝望关键词）
- 新增 `_compute_chronicity_bonus()` 方法，命中 1-2 个关键词给一半加成（0.11），3+ 个给满加成（0.22）
- 该加成独立于 intensity 和 safety 计算，直接叠加到最终 risk 分数
- 修复后该用例 risk 从 0.38 → 0.60，成功路由至 COMFORT

## 问题 2：跨轮次重复提问（Cross-turn Repetitive Probing）

**现象：** 用户明确说"我不是睡不着，我是夜里会早醒"，下一轮 AI 依旧询问"大概需要翻来覆去多久才能睡着？"。即使用户已纠正 AI 的推测，AI 仍然在同一个临床维度上重复探测。

**根因（三层递进排查）：**

| 层级 | 位置 | 具体原因 |
|------|------|----------|
| L1 关键词覆盖不足 | `PROBE_DIMENSION_KEYWORDS` 睡眠维度 | 阈值 ≥2，AI 问"多久才能睡着"仅命中"睡"→1 个关键词，未达到检测门槛，`detect_probed_dimension()` 返回 `None`，"睡眠"未被记录为已探测 |
| L2 Prompt 约束弱 | `KNOWLEDGE_SYSTEM_PROMPT` | KNOWLEDGE 模式仅有弱约束"挑还没聊过的方向"，无独立的反重复警告块，LLM 注意力权重不足以遵循 |
| L3 会话持久化缺失（真因） | `InterventionService.astream_intervene()` | 量表路径的 4 个代码出口均未调用 `_save_turn()`——首次触发量表、量表进行中、当前量表完成跳转下一量表、量表完成——全部直接 `yield` / `return`，绕过了对话历史持久化 |

**L3 细节：** `astream_intervene()` 在量表触发时直接 `yield reply; return`，量表进行中的每个出口同理。非流式 `intervene()` 同路径同样缺失调用。导致每轮对话的 user message + AI reply 不写入 MySQL `messages` 表，Redis 缓存也无记录。下一轮 `_format_history()` 从 `get_history_for_prompt()` 取到的始终为空列表。

**修复：**

- L1（`modules/intervention/generator.py`）：睡眠维度关键词从 12 个扩充至 21 个，新增"睡着""躺""床上""休息""翻来覆去""困""累""闭眼""清醒"
- L2（`modules/intervention/generator.py`）：KNOWLEDGE prompt 增加独立 `⚠️ 禁止重复提问` 段落 + "用户纠正时立刻接受"子规则
- L3（`modules/intervention/service.py`）：在量表路径的 4 个出口全部补入 `_save_turn()` + `_save_probed_dimension()` 调用

## 问题 3：量表系统重复出题（Scale Question Repetition）

**现象：** PHQ-9 量表触发后出 Q1（兴趣减退），用户回答后系统重新出 Q1（完全相同的维度），量表不推进到 Q2。

**根因：**

### 3.1 量表状态不持久（已被问题 2-L3 修复覆盖）

量表状态 `scale_state` 依赖 `session.save_scale_state()` → Redis/MySQL 双写维持。若持久化失败，下一请求 `_get_session()` 重建 `TherapySessionMemory` 实例时 `scale_state=None`，量表被当作"首次触发"重新 `start()`，从 Q1 重新开始。

### 3.2 量表出题 LLM 无上下文

`ScaleOrchestrator._generate_question()` 使用 `QUESTION_PROMPT` 调用 LLM 生成自然语言问题。该 prompt 的 `{context}` 字段在首次出题时固定传入字符串 `"（对话刚开始）"`，且完全不包含对话历史。LLM 在生成问题时对之前对话内容零感知——即使量表状态正常推进，也可能生成与之前轮次语义重复的问题。

**修复：**

- 文件：`modules/intervention/scale/orchestrator.py`
- `QUESTION_PROMPT` 增加 `{conversation_history}` 占位符 + `⚠️ 禁止重复提问` 约束
- `_generate_question()` 签名扩展 `session` 参数，调用 `session.get_history_for_prompt()` 提取最近 3 轮对话注入 prompt
- `start()` 和 `process_turn()` 中全部 3 处调用点传入 `session`

## 诊断日志

为辅助后续排查，在以下位置增加了 INFO 级别日志：

| 日志标签 | 位置 | 用途 |
|----------|------|------|
| `[TURN_SAVE]` | `generator.py:_save_turn()` | 确认每轮对话是否成功保存 |
| `[HISTORY_LOAD]` | `generator.py:_format_history()` | 确认加载对话历史时的轮次数量 |
| `[SCALE:CHECK]` | `service.py:astream_intervene()` | 输出 `scale_state` 完整值，确认量表状态跨请求持久化 |
