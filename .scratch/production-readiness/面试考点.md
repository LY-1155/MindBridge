## 1. 用户认证体系设计（系统设计高频考点）

### 能讲清楚的要点

**user 与 credential 解耦**

```
user_id: "u_abc123"           ← 一个人的永久标识，数据归属
  ├── credential: password    ← 当前登录方式
  ├── [预留] credential: phone   ← 可选，用于危机触达
  ├── [预留] credential: wechat  ← 可选，一键登录
  └── 情绪记录、量表、会话    ← 全挂在 user_id 下
```

换登录方式时 user_id 不变，数据不丢。

**JWT 双 token 模式**

| token | 有效期 | 用途 | 存哪里 |
|-------|--------|------|--------|
| access_token | 30 分钟 | 业务请求鉴权 | 前端内存 |
| refresh_token | 30 天 | 换取新 access_token | localStorage / httpOnly cookie |

为什么两个：access 短→泄露窗口小。refresh 长→不用频繁输密码。refresh 可被服务端吊销。

**为什么 Bearer header 而不是 cookie：** 项目是 SPA 前端，CORS 配 `allow_origins=["*"]` 时 cookie 有 CSRF 风险。Bearer header 不受 CSRF 影响。

## 2. 多 worker 并发模型（Python 后端经典考点）

### async + gunicorn 双层模型

```
gunicorn（进程管理器）
  ├── uvicorn worker 1  ← 处理请求 A
  ├── uvicorn worker 2  ← 处理请求 B
  ├── uvicorn worker 3  ← 视频上传 ffmpeg 阻塞 → 只卡这一个
  └── uvicorn worker 4  ← 处理请求 C
```

- **第一层 gunicorn**：多进程，一个 worker 的同步阻塞（模型推理、ffmpeg）不影响其他 worker
- **第二层 async**：单 worker 内 async，解决 I/O 等待（数据库查询、LLM API 调用），等待时 worker 可以接下一个请求

### 内存缓存在多 worker 下的陷阱

```python
# 单进程 OK，多进程失效
class SessionManager:
    _sessions: Dict[str, Session] = {}  # ← 每个 worker 有自己的拷贝

# Worker 1 存了 session_aaa
# gunicorn 下一次请求分给 Worker 3 → 没有 → 又重新查一次数据库
```

生产环境去内存存储，用 Redis 做跨 worker 共享的热数据。

## 3. 数据安全三板斧（能串起来讲）

### 传输层：HTTPS + Nginx TLS 终止

```
用户 → HTTPS(公网) → Nginx(TLS 终止) → HTTP(内网) → uvicorn
```

### 存储层：字段级 AES 加密

| 加密（存密文） | 不加密（存明文） | 理由 |
|----------------|-----------------|------|
| messages.content | session_id, user_id | 明文字段需要建索引、做关联查询 |
| emotion_records.context | emotion 标签名, risk 值 | 标签名是枚举，无 PII |
| safety_flags.matched_terms | created_at, reviewed | 时间戳和设备无关 |

密钥存环境变量 → 入侵者拿到数据库也解不开内容。

### 应用层：分级速率限制

```
全局        60 req/min/user
登录注册    3~10 req/min/IP    （防暴力破解）
视频分析    3 req/min/user     （昂贵操作）
crisis 接口  无限流             （危机场景不能挡）
```

为什么用 slowapi + Redis：FastAPI 生态标准件，项目已有 Redis，不需要新服务。

## 4. 危机短路的全链路（业务安全，面试区分度最高）

### 核心流程

```
用户输入 → 安全过滤
  ├── level=0 → 正常管线
  ├── level=1 → 记录 safety_flags 表 → 正常管线 → 但累积规则在后台跑
  │       └── 同 user 7 天内 level=1 累积 N 次 → 自动升 crisis
  └── level>=2 → 安全短路 → 跳过情绪分析和路由 → 直接 crisis 干预
                       └── EmergencyPushService 真实推送
```

### 为什么 crisis 接口不限流

被 429 挡住的不可以是危机中的人。

### 为什么会有"累积规则"

没人 7×24 值班盯 level=1——用纯规则代替人工审查。同一 user 滑动窗口内多次 level=1 → 自动升级。

### 静默失效怎么防

数据库写入失败不能 `print()` 后继续。CRITICAL 级 → webhook 推钉钉/飞书。

## 5. 数据库 Schema 演进（能讲清楚从 demo 到生产的改造）

### 旧设计（demo）

```
sessions ─┬─ messages
          └─ emotion_records(intensity = int 1-10)
```

问题：没有 user 实体，session_id 就是"用户"。安全结果不入库。

### 新设计（生产）

```
users ───── credentials（多因子绑定）
  │
  ├── sessions ─── messages（content AES 加密）
  │          └── emotion_records（intensity=float, risk=float）
  │
  ├── safety_flags（level, matched_terms AES 加密, reviewed）
  │
  └── scale_screenings（PHQ-9/GAD-7, responses JSON, scores JSON）
```

### Alembic 为什么必须接

`Base.metadata.create_all()` 只会"表不存在就建，存在就跳过"——不会检测列变更。一旦有真实用户数据，加字段不能靠 drop_all + create_all。
